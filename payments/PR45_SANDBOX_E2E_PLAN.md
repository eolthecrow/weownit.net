# PR #45 sandbox deployment and end-to-end plan

Status: preparation only. Do not deploy until the checks below are evidenced for the exact account, resources, code revision and rollback target. Keep Stripe in test mode and the public Store and main branch untouched. Never put credentials in this document or a transcript.

## Release gates

1. Compare the existing local work with PR #45 and review the combined changes, including the optional recovery flow and revocation interaction. Run unit, integration and desktop/mobile browser tests on the final commit. Confirm CI for that exact commit.
2. With the account owner, confirm the authenticated Cloudflare account ID and the separate `weownit-payments` Worker and its workers.dev URL. Inspect deployed version, routes, bindings and flags; verify it does not serve the public Store. Match the D1 UUID in the local configuration to the intended `weownit_r2_budget` database and confirm `weownit-toolkits` is the intended private R2 bucket with no public access. Verify access and permissions without changing data.
3. Confirm Stripe account and sandbox identity match the Worker test key, webhook destination and test Products/Prices. Check that no live key, live endpoint or live product is involved. Check the test webhook signing secret exists without exposing it. Ensure admin authentication and the intended flags are configured on the isolated Worker.
4. Record the current Worker deployment/version and its source revision, configuration, flags, bindings and secrets availability. Confirm the prior version can actually be redeployed or rolled back and that required schema is backward compatible. Record a D1 backup/restore or time-travel recovery point and R2 recovery approach, permissions, and operator. Additive tables and purchase history must remain intact; do not delete or restore over active data as a routine rollback. Test rollback procedures in an isolated environment if necessary.
5. Review the guarded deployment script: it runs remote migrations before deployment. Verify every schema and migration against the actual D1 state, including quantity and recovery tables, and rehearse on a disposable copy. Do not run it until authentication, identities, recovery and test gates are verified. Establish the exact feature flags; public catalog and recovery remain off unless intentionally tested. Review browser-bound access expiry and operational limits.

## Sandbox E2E execution after gates

1. Record deployment version, time, flags, URL, test operator and isolated test identifiers. Confirm `/health` and authentication, and that unsigned/invalid webhook requests are rejected. Verify the deployed Stripe key and endpoint are test-mode through the respective dashboards; do not print secrets.
2. From `/admin`, create a uniquely named test Product and fixed one-time RON Price. Refresh and verify corresponding test-mode Stripe objects and price. Upload a small known ZIP with a recorded checksum; verify a unique object in the private R2 bucket, no direct anonymous access, and successful association with the Price in D1 through admin. Check malformed, oversized and unauthorized uploads fail without overwriting objects.
3. Verify the new product starts Draft; preview RO/EN/FR and inspect title, amount and ZIP metadata without disclosing the private object key. Publish in staging, verify listing and checkout gating when the staging catalog flag is enabled, then unpublish and confirm new checkout is blocked. Republish for the payment test. Check edits and archive/restore return it to Draft; verify stale revisions fail safely.
4. In each customer language, check desktop and mobile layout, keyboard navigation, labels, and checkout links. In the same browser start a test Checkout, pay with Stripe's current documented test payment method, and retain test session and event IDs. Confirm a signed test webhook was accepted, the event and paid amount/currency/quantity match Stripe and D1, and a duplicate event is idempotent. Invalid signatures, unpaid or mismatched sessions must create no entitlement.
5. Return in the original browser, obtain the ticket, download the ZIP and compare its checksum to the uploaded file. Confirm a different browser, guessed/invalid ticket, unpaid session, expired ticket/access and exhausted download limit cannot download. Exercise duplicate webhook delivery and concurrent claims without duplicate grants or excess uses. Confirm signed-in admin can revoke both before ticket issuance and after issuance; receipt, download and recovery must fail thereafter. If recovery is deliberately enabled, verify one-time email recovery, replay, expiration, transfer of browser ownership and revocation both before and after link issuance.
6. Record HTTP statuses, timestamps, test-only IDs, deployment version, relevant redacted logs and pass/fail for every case. Check no ZIP content, ticket, API key or signing secret appears in logs. Stop on unexpected results, disable sandbox flags as appropriate, and use the verified rollback procedure. Preserve D1/R2 evidence and do not delete historical purchases or objects.

## Exit criteria

All release gates and E2E cases pass on the exact candidate; the account owner confirms resource identities and rollback readiness. Any missing access, failed test, unverified identity, missing rollback or uncertain Stripe mode is a deployment blocker. This plan alone is not evidence that a remote payment, webhook, download, or rollback succeeded.
