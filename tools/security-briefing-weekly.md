# Weekly Security Briefing

The latest edition groups published, non-archived articles by the Monday of their `publishedAt` date. Older editions and explicitly archived records remain on the Briefing page and retain their original URLs. If there is no later edition, the latest remains visible. Searches and category filters include both current and archived records.

On Sunday at 16:17 Europe/Bucharest, the scheduled workflow collects recent source titles into the GitHub Actions artifact `briefing-candidates`. These are unreviewed candidates, not finished articles or guaranteed recent results. Check the original sources, dates, relevance, applicability and technical recommendations; deduplication compares exact URLs only. Partial errors are included in the artifact. No message is sent. GitHub may delay or skip scheduled runs; dispatch the workflow manually if needed.

To approve a future story, add a unique record to `content/security-briefing.json`, include original HTTPS sources and complete EN/RO/FR fields, set `status` to `published`, and set the future `publishedAt` and a review date on or before the publication date. Repository contents are public: future records committed to the repository are not confidential even though the generator does not include them in the public pages until the due date. Do not commit sensitive drafts. Run `python -m unittest discover -s tests -p test_security_briefing.py` and `python tools/build_security_briefing.py --check`.

On Monday at 08:23 Europe/Bucharest the publication job rebuilds eligible articles. If anything changes, it opens a pull request; merge after reviewing it to publish through the existing site deployment. This last merge is manual: GitHub Actions must be allowed to create pull requests in repository settings. No PR is created when there are no changes. The workflow can also be run manually. If the scheduled run is skipped or permissions deny the PR, no publication occurs; the current edition remains online. GitHub's default token does not reliably trigger other workflows on a direct push, so publication deliberately uses a reviewed PR rather than claiming that a bot push guarantees deployment.

Telegram and automatic delivery are not configured. Git history retains previous versions; corrections should keep the same slug and update `reviewedAt`. Keep original source attribution and never treat candidate headlines as verified remediation advice.
