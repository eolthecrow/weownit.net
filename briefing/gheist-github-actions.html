Gheist: when a GitHub token exposes deployment secrets

CI/CD abuse can reach service and infrastructure credentials. Deleting the workflow does not close the incident.

weownit.net editorial analysis · weownit.net publication: 2026-10-26 · Reviewed: 2026-10-26

Topic

GitHub · CI/CD · Secrets

Original source

Wiz Research ↗ · GitHub Docs — Secure use ↗

In focus

Documented campaign

What was reported

According to Wiz, Gheist uses stolen tokens to introduce workflows that extract secrets through GitHub Actions logs.

Applicability and impact

Relevant to teams deploying applications, running network automation or storing cloud credentials in CI/CD. Repository access can have consequences beyond GitHub. A self-hosted runner also requires host assessment, not only branch cleanup.

What to check and remediate

  1. Check: look for ci-sync- branches and sync-check.yml in repository history and audit logs. Preserve evidence before cleanup; a name alone does not establish compromise.
  2. Contain: stop suspicious runs and revoke the implicated token. Identify every repository, environment and service it could reach.
  3. Remediate: rotate potentially accessible secrets and update their consumers in a controlled order. Review subsequent access in cloud services and managed systems.
  4. Prevent: limit write access and require review of workflow changes; use protected environments where your plan supports them, and short-lived credentials with restrictive trust policies.
  5. Validate: run a benign deployment using the new credentials, confirm old credentials are revoked and inspect target-service logs. Do not execute the suspicious workflow as a test.
What to keep in mind

Target outcome: retired old credentials, constrained access and a verified working deployment. A missing workflow does not prove secrets were never read.
